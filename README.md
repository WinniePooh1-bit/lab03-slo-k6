### 2. SLO Хүснэгт

| Сценарио | SLI (юуг хэмжих) | Босго | Цонх / нөхцөл | Үндэслэл |
| :--- | :--- | :--- | :--- | :--- |
| **Performance** | `/cart/add` latency | p95 < 15 мс | 20 VU, 1 мин | Localhost дээр хурдан (1-5мс) тул p95 < 15мс гэж бодит чанга босго тогтоосон |
| **Reliability** | `/pay` error rate | < 8% | 20 VU, 1 мин | Серверт ~5% алдаа суулгасан тул 8% нь тохиромжтой |
| **Availability** | Нийт хүсэлтийн амжилт | ≥ 90% | 20 VU, 2 мин | 10 сек зогсолтод error budget хүрэх боломжтой |

* **Error Budget тооцоо:** 2 минутын цонхонд 90% availability гэдэг нь 12 секундийн зогсох эрх (Error Budget) юм.

---

### 3. Дүгнэлт

Сценариог SLO болон k6 threshold болгон шилжүүлэхэд хамгийн хэцүү хэсэг нь бодит систем болон орчинд тохирсон чанга бөгөөд бодитой босго сонгох байв. Стандарт 200мс босго нь Localhost дээр юу ч хэмжихгүй сул байсан тул `/cart/add`-д p95 < 15ms чанга босго тогтоосон. Chaos туршилтаар серверийг 10 секунд Ctrl+C хийн зогсооход хүсэлтүүд шууд connection refused алдаа зааж агшин зуур буцаж байсан. Үүнээс үүдэн хүлээлтийн хугацаа алга болж зогсолтын 1 секундэд хэвийн үеийнхээс олон хүсэлт унасан тул хүсэлтийн хувиар тооцсон availability эрс буурсан. Энэ нь цагаар тооцсон error budget болон хүсэлтээр тооцсон error budget яагаад зөрдгийг батлан харууллаа. Мөн сервер зогсоход `/pay` endpoint унаж reliability threshold зэрэг FAIL болсон нь нэг эвдрэл олон SLO-д зэрэг нөлөөлдгийг харуулав. Зориуд FAIL болгосон туршилтаар k6 нь exit code != 0 буцааж CI/CD pipeline-д build зогсоох боломжийг олгодог болохыг шалгалаа.
