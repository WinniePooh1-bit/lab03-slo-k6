### 3. FAIL Туршилтын Мэдээлэл

`slo-test-fail.js` скриптийг ажиллуулахад k6 нь босго задарсныг илрүүлж `results/fail.txt` файлд дараах алдааг бичсэн:
* **Лог мэдээлэл:** `level=error msg="thresholds on metrics 'http_req_duration{name:cart}, http_req_duration{name:report}' have been crossed"`
* **Exit Code:** `exit=99`

### 4. Дүгнэлт

Сценарио тус бүрийг SLO болон k6 threshold болгон буулгахдаа системийн бодит ажиллагаанд тохирсон хэмжүүрийг оновчтой сонгох шаардлагатай байв. Localhost орчинд `/cart/add` endpoint нь маш хурдан буюу p(95) нь 1.95ms байсан тул стандарт 200ms босгоос илүү бодитой p(95)<15ms босго тогтоосон. Хэвийн ажиллагааны (`pass.txt`) үед `/pay` endpoint-ийн алдааны хувь 3.77% гарч, нийт хүсэлтийн availability 98.74% (2746/2781) байж 90%-ийн босгод амжилттай хүрсэн. Chaos туршилтын үеэр серверийг түр зогсооход сүлжээний холболт тасарч connection refused алдаа үүссэн. Сервер зогссон хугацаанд хүсэлтүүд хүлээгдэлгүй шууд унаснаас болж нэгж хугацаанд унасан хүсэлтийн тоо огцом нэмэгдэж, хүсэлтээр тооцсон availability 81.29% (4680/5757) болж буурсан. Энэхүү уналтаас үүдэн availability шаардлага хангагдаагүйгээс гадна `/pay` endpoint-ийн алдааны хувь 21.93% болж эрс өссөн. Энэ нь нэг эвдрэл буюу серверийн зогсолт нь availability болон reliability гэсэн хоёр SLO-д нэгэн зэрэг сөргөөр нөлөөлдгийг батлан харууллаа. Зориуд FAIL болгохоор бэлтгэсэн туршилтад k6 нь босго давсан алдаа заан stderr дээр "thresholds ... crossed" лог үлдээж, exit code 99 (`exit=99`) буцаан ажиллагааг дуусгасан. Ингэж exit code 0-ээс өөр гарагснаар CI/CD pipeline дээр чанарын шаардлага хангагдаагүй системийг автоматаар зогсоох боломж бүрддэг болохыг практикаар баталгаажууллаа.
